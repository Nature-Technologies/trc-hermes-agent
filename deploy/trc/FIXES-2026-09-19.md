## H1 — Native toolset not restricted; ~30 non-ragnarok tools on the wire  🔴 first

**Evidence.** `deploy/trc/config.yaml` has no `platform_toolsets.api_server`. The API
server therefore resolves the default `hermes-api-server` toolset (`toolsets.py:401`):
`terminal`, `process`, `read_file`, `write_file`, `patch`, `search_files`,
`web_search`, `web_extract`, twelve `browser_*`, `execute_code`, `delegate_task`,
`cronjob`, `skill_manage`, `image_generate`, `vision_analyze`, plus the five
`mcp__ragnarok__*` tools. The system prompt bans them by instruction only; ROADMAP
records the model running `search_files` anyway.

**Fix** (`deploy/trc/config.yaml`):
```yaml
platform_toolsets:
  api_server:
    - ragnarok          # MCP server name resolves as a toolset (toolsets.py:636-660)
```
If `resolve_toolset("ragnarok")` returns None on the deployed build, use
`disabled_toolsets` listing every non-MCP toolset instead, and file the alias bug.

`ingest_document` must also disappear from the end-user surface. Hermes has no
per-server tool allowlist in `tools/mcp_tool.py` (only `enabled_toolsets` /
`disabled_toolsets`), so the cut has to happen on the backend side: mount it on a
separate MCP path or gate it on a service credential. Tracked as backend B6-adjacent;
until then the prompt ban stands.

**Verification.** `hermes tools --platform api_server` lists only `mcp__ragnarok__*`
tools — six once backend B6 lands `read_document`, five before it; the count is the
backend's to change, and what this item asserts is that NOTHING ELSE is on the wire.
The next OpenRouter export's `tools` array, if visible, agrees. The session-level
`system_prompt`
no longer contains "# Tool-use enforcement" or `<available_skills>`.

## H3 — Hermes rebuilds history from the Open WebUI body; prior tool calls vanish  🔴 code

**Evidence.** Export 2 (turn 2 final) has two `query` tool calls and two tool results.
Export 3 (turn 3 final) has none of them — only the outlet-rendered assistant
paragraph. Hermes' own session file holds all four tool calls. Both requests have
exactly ten messages by coincidence, not a cap; the only history limit
(`RESPONSES_AUTO_TRUNCATION_HISTORY_LIMIT = 100`) is on the Responses endpoint.

**Root cause.** `gateway/platforms/api_server.py` ≈4040-4062: without
`X-Hermes-Session-Id`, `history = conversation_messages[:-1]` from the body;
`_derive_chat_session_id(..., chat_id=get_end_user_chat_id())` only names the session
for persistence. Stored history is write-only on this path.

**Fix** (choose one; A is recommended because it needs no Open WebUI change):
- **A. Hermes-side.** When `X-OpenWebUI-Chat-Id` is present and a session with the
  derived id already exists in state.db, load `db.get_messages_as_conversation(
  session_id)` as history and use only the body's LAST user message. Fall back to
  body history when no stored session exists (first turn) or the load fails.
  Guard: body's prior turn count and stored turn count should agree; if the body has
  fewer user turns than the store (user deleted / regenerated a message in Open
  WebUI), prefer the body and log a divergence warning.
- **B. Open WebUI-side.** Send `X-Hermes-Session-Id: api-<sha256(chat_id)[:16]>` from
  the fork's `routers/openai.py` next to the chat-id header. Hermes' existing
  continuity path then loads stored history. Requires the API key gate (already set:
  `API_SERVER_KEY`).

Either way, compaction (`compression.threshold 0.50`) now matters: 35 K tool results
per turn accumulate. Confirm compression triggers on this path; consider dropping tool
results older than two turns to a one-line stub.

**Verification.** Turn N+1 OpenRouter export contains turn N's `mcp__ragnarok__query`
call and its result. Session file and wire history agree on message count.

## H4 — Loop guardrail hard stop off; 90 turns of external spend possible  🟠

**Evidence.** `hermes_cli/config.py:1399` `hard_stop_enabled: False`;
`agent.max_turns: 90`; session `model_config.max_iterations: 90`.

**Fix** (`deploy/trc/config.yaml`):
```yaml
agent:
  max_turns: 12
tool_loop_guardrails:
  hard_stop_enabled: true
  hard_stop_after:
    exact_failure: 3
    same_tool_failure: 4
    idempotent_no_progress: 3
```
12 turns is enough for query → read_document ×3 → answer once B6/B8 land.

**Verification.** Force a failing MCP call; loop stops with a user-visible message
after 3 identical failures.

## H5 — MCP tool timeout 300 s; user waited five minutes on a stall  🟠

**Evidence.** Turn 2a: tool call 10:40:05, backend generation finished 10:40:57, Hermes
timed out 10:45:05. `tools/mcp_tool.py:345` `_DEFAULT_TOOL_TIMEOUT = 300`.

**Fix.** Set per-server timeout to match the backend's new deadline (B5, 150 s):
```yaml
mcp_servers:
  ragnarok:
    url: http://app:8000/mcp
    forward_user_identity: true
    timeout: 160
```
The model's own "let me try once more" retry is acceptable behaviour; do not add an
automatic retry in Hermes — a second 150 s wait doubles the damage.

**Verification.** Simulated stall returns to the user in ≤ 3 minutes with a clear
timeout message.

## H6 — Model drift: config says `minimax/minimax-m3`, session ran `deepseek/deepseek-v4-pro`  🟡

**Evidence.** `deploy/trc/config.yaml` `model.default: minimax/minimax-m3`. Session file
`model: deepseek/deepseek-v4-pro`; every Hermes-tagged OpenRouter row is deepseek.
The minimax rows (≈350 prompt tokens) are the `auxiliary.status_hints` side calls.

**Candidates.** (a) Dashboard-persisted config on the volume overrides the uploaded
`config.yaml` (commit `05191f977` changed the upload path — verify which file wins).
(b) Open WebUI sends a `model` field that Hermes accepts as a raw session model
(`api_server.py:536`, `session_model` precedence in `_create_agent` docstring).

**Fix.** Pin the served model: define one `model_routes` alias (`trc-assistant`) in
`platforms.api_server.extra`, expose only that alias on `/v1/models`, and have Open
WebUI select it (O4). Make `config.yaml` the deployed truth: dashboard edits should
not survive a deploy. Choose the model deliberately: the backend generation model and
Hermes reasoning model should be recorded together in the runbook with their data
retention terms.

**Verification.** `GET /v1/models` lists one alias; session files show the pinned
model; OpenRouter rows tagged "Hermes Agent" all use it.

`choose_history` was extracted rather than left inline because its rule is the whole

client's is shorter (a deleted or regenerated message), counted in user turns. Writing

"stored wins when it is at least as long", which is the same thing in the normal case
and exactly backwards in the case the guard exists for.

### H7 — still open, and it is a live check, not a code change

Once H3-A is deployed the stored session is load-bearing, so the retention sweep's
derivation (`api-<sha256(chat_id)[:16]>` in trc-backend) has to be confirmed against a
real Hermes. It cannot be verified from this repo:

1. open a chat in Open WebUI on staging, ask one question that calls `query`;
2. `ls $HERMES_HOME/sessions/` on the host — note the `api-…` id;
3. delete the chat in Open WebUI;
4. confirm the backend's `DELETE /api/sessions/{id}` hit THAT id (sweep log line), and
